# Changelog — v1.0.0 (2026-10-17)

## Changes — 2026-10-21
- Checked `hfinit.py`, `vps.py` and `vps-pull.sh` against the current remote `main` layout (cloned separately - `main` is `60ed56f "before switch"`, a history with no common ancestor with this branch) and fixed the three things that did not work there. (1) `main`'s `pyproject.toml` declares `pyarrow>=17` but not `huggingface_hub`, so `uv run hfinit.py` died with `[ERROR] huggingface_hub is not installed ... Try: uv sync` - and `uv sync` could not help, because the dependency was never declared. This branch already had it; `main` needs `"huggingface_hub>=1.0"` added. (2) `hfinit.py --cdc` called `pq.write_table(..., use_content_defined_chunking=True, write_page_index=True)` with no compression arguments, so PyArrow fell back to its default snappy and a 10,487-byte zstd-19 batch came back as 28,599 bytes - 2.7x larger, silently undoing the level-19 choice `text_collect.py` documents as ~40% smaller on segmented Burmese text. `rewrite_with_cdc` now reads the source codec and reuses it (zstd level 19), which brings the same rewrite to 11,421 bytes, 1.09x, the page-index and chunk-boundary overhead; it also refuses to run when the work dir is the source dir, which would otherwise have overwritten the original file. (3) `vps-pull.sh` defaulted to a single `books.parquet`, which `main`'s `text_collect.py` never writes - it writes one `batch-<YYYYmmdd-HHMMSS>.parquet` per run - so the bare invocation could not work at all. With no name given it now pulls every remote `*.parquet`; naming a file or setting `VPS_REMOTE_FILE` still narrows it to one and `--all` is unchanged. `DEFAULT_REMOTE_FILE` is gone.
- Rewrote `hfinit.py`'s docstring, which described this branch's cumulative `books.parquet`, to describe `main`'s actual layout: one `batch-<stamp>.parquet` per run in `pdfs/parquet/`, four columns `author | book | text | segmented`, and `pdfs/parquet/ocr/` left alone because folders are not walked. Because batch names never repeat, every push is an ADD and the repo grows as shards that all share one schema, so the Hub, `datasets` and duckdb read the folder as one table; UPDATE only fires when the same batch name is pushed again, which is a retry, where replacing the file is correct and cannot duplicate rows.
- Verified inside a clone of `main`, against a local stub of the Hub API and a fake ssh VPS: login; first push of three batches as ONE commit with the `ocr/` subdir and the `.batch-<stamp>.parquet.tmp` dot-temp both skipped; re-push classifying as UPDATE; the bytes landing on the Hub byte-identical to the local file; `--cdc` landing as ZSTD with the table unchanged; bare `vps-pull.sh` pulling all three batches sha256-verified with `notes.txt` and the dot-temp skipped and the VPS copy untouched, argv showing `-i ~/.ssh/mylinux -o IdentitiesOnly=yes`; named-file, `VPS_REMOTE_FILE` and `--all` all still narrowing correctly; unreachable VPS exit 1. Not verified against the real Hub or the real VPS, which this sandbox cannot reach, and the Xet chunk savings `--cdc` promises still could not be measured here.
- Added `hfinit.py` and deleted `hf-upload.sh`, which it replaces. With no argument it only logs in: it reads the `HG_TOKEN` access token (the one named `hg_full`) or prompts for it, stores it in the Hub cache with `huggingface_hub.login`, and confirms the identity with `whoami`. With a cwd-relative file or folder argument it pushes every `*.parquet` directly inside that folder (not recursive, and dot-files are skipped so the `.books.parquet.tmp` half-writes left by `text_collect.py` are ignored) into ONE hardcoded private dataset repo, `datasets/htetmyetflam3/scraper` - the user name and repo name are two obvious lines at the top of the file - created on first run. There is deliberately no repo listing or repo picker: one repo holds every dataset, and separate datasets inside it are separate Hub configs, which is what gets its own dropdown and viewer URL. Each file's name is compared against the repo's existing file list; a name already present is UPDATED in place and a new name is ADDED as a new dataset file, and every file in a run goes into a single commit through `create_commit`/`CommitOperationAdd` because the Hub allows only about 320 commit creations per hour. UPDATE replaces the file on the Hub with the local copy and merges nothing on this machine, which is correct only because the local Parquet is cumulative (`text_collect.py` appends each book into `books.parquet` and rewrites it atomically), so replacing it is the append. The token is validated with `whoami` before any upload work, because `create_repo(exist_ok=True)` deliberately swallows 401/402/403 - without that check a wrong token fails part way through a commit with a message that never mentions authentication.
- Added an opt-in `--cdc` flag to `hfinit.py`: it rewrites each Parquet with `use_content_defined_chunking=True` and `write_page_index=True` before uploading, so later row updates transfer only the changed ~64 kB Xet chunks instead of most of the file. It needs `pyarrow>=21`; `pyproject.toml` still says `>=17`, and the flag fails loudly with the reason rather than silently uploading the un-optimised original if the installed PyArrow is older. The first `--cdc` run costs one full re-upload because every chunk boundary moves at once. The rewrite is checked to preserve the row count before it is uploaded.
- Pointed `vps-pull.sh`'s "next:" hint and the `pyproject.toml` dependency comment at `hfinit.py`. Verified against a local stub of the Hub API (login, bad token, not logged in, first push creating a private repo, repeat push classifying as UPDATE, mixed new+existing in one commit, uploaded bytes identical to the local file, and `--cdc` output equal as a table); NOT verified against the real Hub or the real VPS, which this sandbox cannot reach, and the Xet chunk savings `--cdc` promises could not be measured here.
- Added `vps.py`, a one-shot `ssh hostingervps` wrapper for the local container: `uv run vps.py --upload LOCAL REMOTE_DIR` and `uv run vps.py --download REMOTE LOCAL_DIR`, where the flag order is the only difference between the two directions. The local side is relative to the cwd; the remote side resolves against the VPS account home, read once over ssh with `echo $HOME`, so a quoted `~/scraper/...` can never expand to the local home. A path ending in `/` (or an existing directory) transfers every file inside it and skips sub-directories, transfers stream through `cat` in binary so a 300 KB random-byte file round-trips byte-identical, and a failed download removes its own empty destination file. It reuses the hardcoded `~/.ssh/mylinux` key pinned with `IdentitiesOnly=yes` from `vps-pull.sh`, deletes nothing on either box, and is deliberately simple - no resume, retry waits or sha256 pass, which `vps-pull.sh` still covers for the large Parquet collection.
- Added two operator shell scripts for moving the VPS Parquet to Hugging Face, written in `gitinit.sh` style (`set -euo pipefail`, inline `DEFAULT_*` constants at the top, `[OK]`/`[INFO]`/`[ERROR]` prefixes, loud failure instead of retry logic). `hf-upload.sh` pushes Parquet to a Hub dataset with the `HG_TOKEN` access token (the token named `hg_full`, read from the environment or the repo-root `.env`, never passed as `--token` so it stays out of `ps`): with no argument it uploads the hardcoded `pdfs/parquet/books.parquet` on the VPS, with a cwd-relative path or folder it uploads that instead, and the repo is created on first run as `htetmyetflam3/<parquet-name>`, private by default. `vps-pull.sh` downloads Parquet from the VPS over plain `ssh` in BatchMode through this box's `hostingervps` alias for HostName, Port and User, with the private key hardcoded as `DEFAULT_KEY="${HOME}/.ssh/mylinux"` (gitinit.sh style) and pinned with `IdentitiesOnly=yes`, so only that key is ever offered to the VPS and never a general key used for other hosts; it lists `--all` remote `*.parquet` while skipping dot-temps, resumes a half-finished download with `tail -c +N`, and renames its `.name.tmp` into place only after the local sha256 equals the VPS sha256. Neither script deletes anything on either box; the only file `vps-pull.sh` removes is its own unverified dot-temp.
- `hf-upload.sh` authenticates with the token rather than the `ssh/hf` key: the Hub requires a token to create a private repo and to store Parquet through LFS, so an SSH key alone is not enough on this path. Large Parquet needs no local `git-lfs` - `hf upload` streams it and a rerun resumes an interrupted upload.
- Added `huggingface_hub>=1.0` to `pyproject.toml` so `uv sync` provides the `hf` CLI that `hf-upload.sh` calls; the script falls back to `huggingface-cli` and then to `uv run hf`.
