## Changes — 2026-10-24
- Removed a wrong absolute `SSH_DIR` from `.env.example` that this log introduced one entry ago, and which then broke the owner's VPS. The sample said `SSH_DIR=/domains/whitesmoke-dolphin-474614.hostingersite.com/public_html/pdfs`; the correct value is `SSH_DIR=pdfs`, resolved by ssh against the account home to `<home>/pdfs/convertable/` - confirmed by the owner's own `ls` on the shared host, which shows `domains` and `pdfs` side by side in his home directory. Because `.env.example` exists to be copied (`cp .env.example .env`, as its own header instructs), a freshly created `.env` inherited the bad path and `uv run parse.py` reported a queue directory that does not hold the books. It is now `pdfs`, and no real hostinger path remains anywhere in the tree outside this log.
- The accompanying advice was the actual cause and is corrected in all three places it appeared - `.env.example`, `save_remote.py`'s module docstring, and `USAGE.md`'s Environment section. They claimed shared hosting "usually needs the absolute form", which is what made the absolute path look like the right thing to ship as a default. The truth is the opposite for this host: relative is the normal case and absolute is the exception, warranted only when the files genuinely live outside the account home. Both files now also state that the value is used **verbatim** - no `~` expansion and no spaces - because the owner's own attempt, `SSH_DIR=~ /pdfs/`, failed for exactly those two reasons: the tilde is never expanded and the space makes the value `~ /pdfs/`, a path containing a space that matches nothing.
- Recorded because the diagnosis went wrong before it went right, and the wrong turn cost the owner several round trips. With no `.env` present in the repo root yet `parse.py` still printing a populated queue path, the only source left in `load_config()` is `os.environ`, which it reads before the file - so the conclusion was that the values must be exported in the shell, and the advice was to hunt through `~/.bashrc` and `/etc/environment`. That reasoning was sound about the precedence and wrong about the facts: a new `.env` had in fact been created, by copying the sample, and it supplied the value itself. The generalisable error is treating "the file does not exist" as still true one turn later, and preferring a clever explanation to checking whether a file this repo ships contains the offending string. A single `grep -rn whitesmoke .` would have found it immediately, and it was only run after the owner said outright that the path looked hardcoded - which, in the sample, it was.

- Widened the duplicate guard to the second identity a book has, so it also stops **the same book under a different name**. As committed an hour earlier the guard keyed on `sha256` alone, which catches the same PDF re-added and the same PDF sitting in `convertable/` under two filenames - but not the same book fetched from a different source, because that copy is a different file with a different hash and identical words. `write_parquet_rows` now indexes the collection by BOTH identities and resolves an incoming row against the file hash first and the exact text second. The outcomes: same file and same text -> denied, a plain re-add; same text under a different name -> denied, which is the case the owner asked for; same name and same text from a different file -> the row is kept and its hash corrected (`[parquet-fix]`), since a re-download of the same book should not open a second entry; same file with different text -> the row that already holds that PDF is updated in place (`[parquet-update]`) rather than a second book being opened for one file. The text arm needs no hash, so it already protects rows written before the column existed, i.e. before `shafill.py` has been run; that is a real improvement over a hash-only guard, which is blind until round one finishes. - Added two operator shell scripts for moving the VPS Parquet to Hugging Face, written in `gitinit.sh` style (`set -euo pipefail`, inline `DEFAULT_*` constants at the top, `[OK]`/`[INFO]`/`[ERROR]` prefixes, loud failure instead of retry logic). `hf-upload.sh` pushes Parquet to a Hub dataset with the `HG_TOKEN` access token (the token named `hg_full`, read from the environment or the repo-root `.env`, never passed as `--token` so it stays out of `ps`): with no argument it uploads the hardcoded `pdfs/parquet/books.parquet` on the VPS, with a cwd-relative path or folder it uploads that instead, and the repo is created on first run as `htetmyetflam3/<parquet-name>`, private by default. `vps-pull.sh` downloads Parquet from the VPS over plain `ssh` in BatchMode through this box's `hostingervps` alias for HostName, Port and User, with the private key hardcoded as `DEFAULT_KEY="${HOME}/.ssh/mylinux"` (gitinit.sh style) and pinned with `IdentitiesOnly=yes`, so only that key is ever offered to the VPS and never a general key used for other hosts; it lists `--all` remote `*.parquet` while skipping dot-temps, resumes a half-finished download with `tail -c +N`, and renames its `.name.tmp` into place only after the local sha256 equals the VPS sha256. Neither script deletes anything on either box; the only file `vps-pull.sh` removes is its own unverified dot-temp.
- `hf-upload.sh` authenticates with the token rather than the `ssh/hf` key: the Hub requires a token to create a private repo and to store Parquet through LFS, so an SSH key alone is not enough on this path. Large Parquet needs no local `git-lfs` - `hf upload` streams it and a rerun resumes an interrupted upload.
